**判据不是一个 Top1 总分**：test 集上 **A = LLM + 告警字典**（0.2 门禁对象）与 **C = 规则引擎同集基线**（旧 8 例 85.7%）各跑一次；**B = LLM + 字典 + 设备信号特征只在 dev 做消融**，不占留出集。另附 `top1ByOrigin`（逐假设记 `origin`，本期由 `evals/metrics.ts` 的 `ObservedHypothesis` 增字段、评测脚本透传）与 `hintOnlyTop1` 朴素基线。**门禁只落 A 组总分（Top1 / Top3）**；`top1ByOrigin.LLM` 是来源披露指标、不设硬门禁 —— 若低于 9/14，交付报告必须显式写明"提升中含规则补位（`RCA_RESCUE`）成分"，不得只报总分。防刷分的主判据是 `hintOnlyTop1` 与 dev 消融的 `B-A ≥ 20 点`。

**A|C 分层**按团队负责人裁决移出本 PRD，由 QA 在最终验收报告离线出表（A 组与 C 组按 case id 对齐：`A|C答对` 的 case 数及 A 命中数、`A|C答错` 的 case 数及 A 命中数；报计数不报比率，`A|C答错` 分母仅 2~3 例）。
**取舍顺序（写死，用于吵架时拍板）**：拒答正确率 > Top3 > Top1 > 延迟 > token。

- **宁可 Top3 高、Top1 低**：把对的答案排到第 2/3 位，值班人点一下就能确认；把错的答案排在 Top1，值班人会照着做。
- **宁可拒答，不可编结论**：不接受"用 Top1 换拒答率"的任何方案；Top1 落后规则基线 2 例以内可交付（登记风险），落后 3 例以上判不达标。
- **延迟只允许一处来源**：裁剪输出体量（每条假设 verifySteps 1~2 条、actions ≤ 1 条、evidence ≤ 3 条）；**禁止**为省时间砍候选数量或砍证据校验。

## 2. 拒答的产品语义

### 2.1 拒答规则（一条，能被代码实现，不依赖"感觉证据不足"）

拒答不是让模型自由裁量，而是**调用模型之前的确定性闸门**：规则命中 → 直接返回空结论、消耗 0 token；未命中则正常调用模型，模型仍可自行返回空假设（同样算拒答）。两条路径都要能拒答，覆盖率分开统计。

| 编号 | 规则                                                         | 判定式（可直接实现）                                                                                                                                       | 命中示例                                                         |
| ---- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| R1   | 类型与时间双重失效：告警侧无一条可归因，变更侧也没有一条能用 | 未抑制告警 `.every(a => classifyAlertType(a.type) === 'UNKNOWN' && familyOf(a.type) === 'OTHER')` **且** `changes.every(c => c.changedAt >= firstAlertAt)` | test-07（3 条 `UNKNOWN_SENSOR_*` + 唯一变更在故障之后）、test-16 |

**只有一条规则的三个理由**（写给后续想加规则的人）：

- **"变更晚于首告警"单独不构成拒答**：它只说明这条变更不能当原因，不说明告警本身不能归因。test-05 就是「事前无事、事后有人改配置」的干扰例，类型已登记，必须出结论 —— 一旦把时序单独设为拒答条件，会把这个当前正确的场景直接判死。
- **"证据条数少"也不构成拒答**：单条 `PACKET_LOSS` 给一条低置信结论 + 采集建议，比拒答对值班人更有用；用条数设阈值会为了规则去造场景，属于自证循环。
- **边界（同样可判定，且必须双向验）**：已登记类型告警 ≥ 1 条即不得拒答（test-10 锁死）；存在晚于首告警的变更但类型已登记，必须出结论且该变更不得被引用为证据（test-05、test-09 锁死）；拓扑缺失（MISSING）不是拒答理由，单设备可定向时必须出结论且 confidence ≤ 0.55（test-11 锁死）。**反向也必须验**：全为已登记 CHILD 类（如 `DNS_TIMEOUT`）、无 ROOT/PARENT、无变更但有标注根因的场景必须出结论（dev-04 锁死）—— R1 只判 `UNKNOWN`，不判 `CHILD`，否则会得到一个把 dev 集判死的门禁。

### 2.2 判定口径

| 判定           | 定义                                                                                                 | 备注                                             |
| -------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 拒答正确       | 标注 `rootCause=null` 的场景，`hypotheses.length === 0` 且 `missingInfo.length ≥ 1` 且每条满足三段式 | 只"空结论"但 missingInfo 为空 → 不算拒答，算缺陷 |
| 漏答（编结论） | 标注 `rootCause=null` 的场景，`hypotheses.length > 0`                                                | 本专项最严重错误，单例即触发风险登记             |
| 误拒答         | 标注 `rootCause !== null` 的场景，`hypotheses.length === 0`                                          | 计入 14 分母；≥ 2 例即不达标                     |

### 2.3 拒答时给用户看什么

- `hypotheses = []`、`summary = null`（沿用 AC-20 现状，不新增字段）。
- `missingInfo` **1~5 条**，每条固定三段式：`[缺口类型] 缺什么 → 为什么缺它就不能定论 → 怎么补（具体设备 / 采集项 / 时间窗）`。缺口类型固定 4 个枚举：`TYPE_UNKNOWN` / `TIMING_BROKEN` / `EVIDENCE_THIN` / `TOPOLOGY_MISSING`。至少 1 条必须是可执行采集动作，例：`[EVIDENCE_THIN] 缺 CORE-SW-01 的 bgpNeighborState 采样 → 无法区分邻居抖动与端口物理故障 → 补采故障前 30 分钟该指标（每 15 秒）`。
- 禁止文案（进验收脚本黑名单）：`请提供更多信息` / `建议进一步排查` / `疑似` / `可能存在问题`。
- 页面空态必须区分**系统拒答（有理由，列 missingInfo）** 与 **研判失败（异常，显示错误码 + 重试）**；这是本专项唯一允许的 UI 改动，不做布局/组件/设计 token 调整。拒答原因随结论落库，复用 `Incident.analysisMeta`（不新增表）。

### 2.4 拒答率上限（防"永远拒答"退化解）

| 场景                              | 上限           | 触发动作                                                   |
| --------------------------------- | -------------- | ---------------------------------------------------------- |
| 评测集误拒答                      | ≤ 1/14（7.1%） | ≥ 2/14 判 0.2 不达标，规则收窄重跑                         |
| 生产灰度（2 周 / 抽样 20 个事件） | 拒答率 ≤ 20%   | > 20% 回查闸门命中分布；> 35% 立即关闸门、只保留提示词约束 |

理由：值班人连续几次点研判都是空结论，就不再点这个按钮。拒答率失控造成的信任损失，比 Top1 低 3 个百分点更致命。

### 3.4 冻结声明（分数可信的前提）

1. 16 个文件的 `MANIFEST.sha256` 即**冻结基线**。此后任何改动都必须记 CHANGELOG 并**重跑「规则 + 真实模型」双基线**，旧分数作废；哈希与清单不一致时评测脚本非 0 退出。**不可删约束。**
2. **test 集只在最终验收跑一次**；调参期间只看 dev 汇总，不看 test 逐场景结果。
3. 分母口径固定为 **14（有标注根因）/ 2（拒答）**，报告头部必须打印清单哈希。**不可删约束。**
4. dev 侧唯一新增是对照实验 **dev-18**（不进 test、不计分、不参与门禁）：仅 `LINK_DOWN` + `PORT_FLAP` + `OPTICAL_RX_LOW`，标注 `LINK`，用于证明告警字典注入没把 category 拉偏。

## 4. 验收标准（EARS）

1. `While` 事件内未抑制告警类型 100% 未登记（`classifyAlertType=UNKNOWN` 且 `familyOf=OTHER`）且所有变更均晚于首个告警，`When` 请求研判，`Then` 系统必须返回空 `hypotheses`、`summary=null`、`missingInfo` ≥ 1 条且含 `TYPE_UNKNOWN`。
2. `When` 拒答闸门命中，系统必须在调用模型前返回，该次研判 `tokensUsed` 为 `null`（未产生 token 消耗；`null` = 没调过模型，`0` = 调了但零消耗，两者不可混用），命中规则编号（R1）写入 `analysisMeta`（复用现有字段，不新增表）。
3. `If` 事件内已登记类型告警 ≥ 1 条（含"全为 CHILD 类、无 ROOT/PARENT、无变更但标注有根因"的情形），`Then` 系统不得拒答，必须输出 ≥ 1 条 `hypotheses`（test-10 正向 + dev-04 反向双向验证）。
4. `While` 事件内存在晚于首个告警的变更但告警类型已登记，`Then` 系统必须输出 ≥ 1 条 `hypotheses`，且任何假设的 `evidence[].ref` 都不得指向该变更（由 test-09、test-05 验证）。
5. `While` 拓扑完整度 = MISSING 且仅 1 台设备上报未抑制告警，系统必须输出 `hypotheses`（confidence ≤ 0.55），不得拒答（由 test-11 验证）。
6. `When` 系统输出假设，每条假设必须满足：`verifySteps` 1~2 条、`actions` ≤ 1 条、`evidence` ≤ 3 条、每条 `desc` ≤ 80 字（不区分 Top1/Top2/Top3，与 `schema.ts` 现有必填性一致）。
7. `While` 系统拒答，`missingInfo` 必须为 1~5 条、每条含 4 个缺口类型枚举之一且为三段式，至少 1 条为可执行采集动作，且不得出现黑名单文案（`请提供更多信息` / `建议进一步排查` / `疑似` / `可能存在问题`）。
8. `While` 跑 test 集（16 例），报告必须同时给出 A/B/C 三组对照、`top1ByOrigin` 分账与 `hintOnlyTop1`，并打印用例清单哈希；缺任一项、哈希与 `MANIFEST.sha256` 不一致或分母不是 14/2 时，评测脚本必须以非 0 退出。
