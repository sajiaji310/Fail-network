# NetScope 项目评审

> 评审对象：`docs/PROJECT-FRAMEWORK.md`
>
> 评审日期：2026-11-19
>
> 评审定位：针对产品方向、工程设计、MVP 可交付性和真实价值验证的初步判断。

## 一、总体判断

NetScope 的方向是对的，框架文档质量明显高于一般个人项目，但当前更像一份**较强的产品与工程蓝图**，还不能算一个已经验证过的系统。

| 维度 | 评价 |
|---|---:|
| 产品方向 | 8/10 |
| 工程设计 | 8/10 |
| MVP 可交付性 | 6/10 |
| 真实价值验证 | 4/10 |

项目最有价值的地方，不是单纯接入 LLM，而是把 LLM 放进一个有明确输入、结构化输出、证据校验、人工确认和案例沉淀的故障处理闭环中。

核心链路可以概括为：

> 告警风暴 → 事件聚合 → 根因假设 → 证据链 → 人工处置 → 复盘沉淀

## 二、值得肯定的地方

### 1. 问题选择真实

“告警风暴 → 事件聚合 → 根因假设 → 证据链 → 复盘沉淀”是一条完整的运维闭环，不是简单套一个聊天框。

目标用户也比较具体：

- 一线运维值班工程师：需要快速知道先看哪里。
- 运维组长 / SRE：需要 MTTR、影响面和复盘材料。

这比泛泛地描述“做一个智能运维平台”更容易形成产品边界。

### 2. 证据校验器是项目最有辨识度的设计

要求 LLM 输出的 `alertId`、`changeId` 和拓扑路径必须真实存在，可以有效约束模型凭空生成证据，也能让研判结果具备一定的可审计性。

这比单纯让模型输出“置信度 0.82”更可靠，因为置信度本身并不能证明结论正确。

但要明确：

> 证据引用存在，不等于根因判断正确。

后续需要区分以下指标：

- 证据引用有效率
- 证据与假设的相关性
- 根因 Top1 / Top3 命中率
- 人工接受率

### 3. 工程边界意识较好

文档明确排除了以下内容：

- SNMP / NetFlow / Syslog 真实采集
- SDN 控制器和网管系统对接
- 自动执行变更或修复
- 多租户和 RBAC
- 移动端
- 自研时序数据库

这些取舍说明项目在主动控制范围，而不是把所有 AIOps 能力都塞进第一版。

### 4. Agent 协作规范比较实用

任务卡、`STATE.md`、单文件行数限制、依赖方向、测试门禁和失败三次上报等规则，能够降低 AI Agent 反复改错、跨模块乱改和产生重复实现的概率。

尤其是以下约束比较有价值：

- 一次只做一张任务卡
- 改动范围提前声明
- 业务规则集中在模块层
- API 必须同步更新文档
- 不确定时查文档，不凭记忆猜 API
- 同一问题连续失败三次后停止并上报

## 三、主要风险

### 1. P0 范围仍然偏大

当前 F1 到 F9 全部被列为 P0，实际上已经覆盖：

- 拓扑编辑器
- 告警导入和模拟器
- 归一化与抑制
- 关联聚合
- AI 研判
- SSE 工作台
- 处置建议
- 复盘报告
- 案例检索

这已经不是一个很小的 MVP。即使代码可以由 AI Agent 快速生成，测试、调试、交互打磨和数据调参仍然会产生大量工作。

更现实的判断是：

- 15 天：可以做出可演示的纵向切片。
- 3 到 4 周：更可能做出结构相对稳定的 MVP。
- 更长时间：才能验证聚合质量和真实运维价值。

### 2. “告警数下降 90%”缺少可执行定义

这个指标现在容易变成宣传口号，需要明确：

- 是原始告警条数减少 90%？
- 还是用户需要处理的事件数减少 90%？
- 重复告警如何计算？
- 错误抑制一条重要告警的代价如何衡量？

建议改成可测试的定义：

> 在 5 套固定故障剧本中，事件数量与原始告警数量的平均压缩比达到目标，同时不得抑制标注为根因的关键告警。

### 3. 聚合算法的难点不只在公式

当前的打分公式清晰、可解释，适合作为第一版基线。但仍需要补充以下行为定义：

- 告警关系是有向图还是无向图？
- 一个告警是否可以属于多个候选事件？
- 事件如何合并和拆分？
- 故障跨越 5 分钟窗口时如何处理？
- 两个故障同时发生时如何避免错误合并？
- 重复运行聚合时，如何保证事件稳定且幂等？

真正困难的部分通常不是“算出一个分数”，而是定义事件边界。

### 4. 告警数据模型存在时间语义风险

当前设计中，`Alert.fingerprint` 是全局唯一，同一指纹的重复告警通过 `count` 累加。

这会带来一个问题：同一设备、同一类型的故障在不同日期再次发生时，系统如何区分新的故障周期？如果永远复用同一条 Alert 记录，历史事件、首次发生时间、结案后的再次发生可能混在一起。

更稳妥的模型是拆分为：

- `AlertFingerprint`：设备、类型、指标组成的稳定定义。
- `AlertOccurrence`：一次实际发生的告警记录或故障周期。

如果暂时不拆表，也至少需要定义：

- 活动窗口
- 重新开启规则
- 结案后的再次触发规则
- `firstSeen` 和 `lastSeen` 的生命周期语义

### 5. 评测集太小，容易得到虚假的高分

10 个标注剧本适合做 demo，不足以证明根因研判质量。人工设计的剧本很容易让系统识别出剧本模式，而不是真正完成根因分析。

评测集至少应增加以下场景：

- 正常噪声告警
- 相似但不同的根因
- 缺失拓扑数据
- 可能误导模型的变更记录
- 两个故障同时发生
- 证据不足
- LLM 输出格式错误
- 引用了存在但不相关的证据

否则 Top1 / Top3 指标可能看起来很好，但不能代表真实环境中的效果。

### 6. “证据校验”容易被误解为“反幻觉已经解决”

当前校验器可以检查证据 ID 是否存在，但不能判断：

- 证据是否支持该假设
- 证据是否只是时间上相关
- 证据是否来自受影响设备
- 拓扑路径是否真的连接到事件范围
- 变更记录是否可能是结果而不是原因

因此更准确的产品表述应该是：

> 通过证据引用校验减少无依据输出，并提高研判结果的可审计性。

不要表述为“解决了 LLM 幻觉”。

## 四、建议优先修改的事项

### P0：先把端到端闭环跑通

建议第一阶段只保留以下链路：

1. 导入或生成 5 套模拟故障数据。
2. 完成告警归一化和基础抑制。
3. 使用固定拓扑完成事件聚合。
4. 展示事件详情和关联告警。
5. 使用规则引擎生成根因候选。
6. 接入 LLM 结构化输出。
7. 对证据引用进行校验。
8. 支持人工确认和结案。

这条链路能够证明项目的核心价值，不需要一开始就完成所有外围能力。

### P1：明确告警与事件的生命周期

补充以下定义：

- 一条 Alert 代表单次告警、告警指纹还是告警周期？
- `ACTIVE`、`SUPPRESSED`、`RESOLVED` 之间如何流转？
- 设备恢复后是否自动关闭关联事件？
- 同一故障跨窗口时是否沿用原 Incident？
- 已结案事件再次出现时，是新事件还是重新打开旧事件？

### P1：补充聚合边界测试

除了空集、单条和全同设备，还需要覆盖：

- 事件跨时间窗口
- 两个相邻但独立的故障
- 同一告警被多个候选簇命中
- 拓扑缺失或链路状态未知
- 父告警晚于子告警到达
- 重复执行聚合
- 大量噪声告警混入

### P1：重新定义评测指标

建议至少保留以下指标：

| 指标 | 含义 |
|---|---|
| 告警压缩比 | 原始告警数量与用户需要处理的事件数量的关系 |
| Incident Precision | 生成的事件中，真正对应故障的比例 |
| Incident Recall | 已知故障中，被成功聚合出的比例 |
| Top1 命中率 | 第一根因假设是否正确 |
| Top3 命中率 | 前三根因假设是否包含正确根因 |
| 证据存在率 | 引用的 ID 是否真实存在 |
| 证据相关率 | 引用证据是否真正支持假设 |
| 人工接受率 | 运维人员是否接受首选建议 |
| 平均研判耗时 | 从事件生成到结果可用的时间 |

### P2：再补充外围能力

以下能力可以后置：

- 拓扑 CRUD 的完整编辑体验
- 案例语义检索
- 复杂报告模板
- 实时推送
- 真实设备数据接入
- 权限系统和多租户

## 五、推荐的第一版范围

如果目标是尽快验证价值，我建议把第一版收缩为：

### 必做

- 固定拓扑种子数据
- 5 套故障剧本
- CSV / JSON 告警导入
- 告警去重和基础抑制
- 基于时间和拓扑的事件聚合
- 事件详情页
- 规则 fallback
- LLM 结构化研判
- 证据引用校验
- 人工确认和结案
- 一组离线评测脚本

### 暂缓

- 拓扑完整 CRUD
- 拓扑拖拽布局持久化
- SSE 流式体验
- 案例相似推荐
- 复杂报告生成
- 多种通知渠道
- 真实网络协议采集

## 六、最终结论

NetScope 是一个**适合做作品集、面试展示和 AI Agent 工程实践的项目**。

它最有说服力的部分不是“用了 LLM”，而是建立了一个可解释、可验证、可追溯的故障研判闭环：

> 归一化 → 聚合 → 推理 → 证据校验 → 人工确认 → 案例沉淀

当前最大风险是：**工程规范已经接近完整产品，但核心算法和数据语义还没有经过足够验证。**

因此下一步不应该继续扩充文档，而应该尽快完成一个最小纵向切片：

> 5 套模拟故障 → 告警归一化 → 事件聚合 → 规则研判 → 证据展示 → 人工结案

只要这条闭环能跑起来，再根据实际评测结果决定哪些设计需要保留、哪些能力应该删除或后置。
