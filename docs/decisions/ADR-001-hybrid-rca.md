# ADR-001：研判链路采用"字典/特征进提示、规则不进答案"的混合架构

## Status

Accepted（2026-11-26，NetScope 0.2 研判质量专项）

## Background

0.1 的研判链路是二选一：有 Key 走 LLM，无 Key 走规则引擎，两条路径互不知道对方存在。实测（test 集 8 场景，7 个有标注根因）暴露出三个事实：

1. 规则引擎 Top1 85.7%，唯一失败是 test-08 的聚类错误；LLM（deepseek-chat）Top1 57.1%、Top3 71.4%。**规则引擎在归因这件事上比 LLM 更准**，因为 `affinity.ts` 的族归类与 `fallback.ts` 的评分承载了团队对现网的领域约定，而模型没有这份约定。
2. LLM 的两处独有失败各有明确根因：test-01 是分类约定没传达（prompt 只渲染 `type/typeLabel`，见 `prompt.ts:77`）；test-07 是校验器不判"证据是否可解释"（`verify.ts` 的 L2 只判存在性与相关性），于是引用真实存在的未登记告警也能通过。
3. 延迟不可控：均值 8969ms、P95 14991ms，P95 那次走了 `analyze.ts` 的"schema 修复重试"即两次调用；`client.ts` 单次 30s 硬超时、`maxRetries=0`、请求体未传 `max_tokens`。

约束：`fallback` 路径必须保持"无 Key 全链路可用"（AC-07）且行为不变；`MIN_CANDIDATE_SCORE=20` 的权重是 T09 调过的，不得为评测让步；不新增第三方依赖、不改数据库 schema。上游产品约束见 `docs/rca-quality/PRD-0.2.md`：test 集扩到 16 例（分母 14/2）、Top1 目标 ≥11/14（最低可接受 10/14）、`REASONING` 阶段 <8000ms / P95 <12000ms、单事件 <4000 token、一次通过率 ≥95%、拒答必须在调用模型前命中。

摆在我们面前的诱惑很直接：把 `ruleFallback` 的 Top1 拼进 prompt，test 集 Top1 立刻从 57.1% 逼近 85.7%。这不是架构，这是把规则引擎的能力记到 LLM 账上。

## Decision

采用混合架构，四条各自可独立回滚：

1. **归因约定以"告警字典"形式进提示，作为证据而非答案。** 逐条告警行尾附 `归因字典:<CATEGORY>`（未登记类型附 `未登记`），段头说明"字典只管 category 字段，不指示根因在哪台设备"，SYSTEM_PROMPT 增冲突条款（现场证据优先、偏离须在 `evidence.desc` 留痕）。标注答案是"类别 + 设备"两元组，字典只覆盖类别一维；设备选择仍需模型自己做。
2. **规则先验只到"特征级"，不到"结论级"。** 提示词新增 `[设备信号]` 段，陈述规则排序时用的同一组事实（告警条数与最高等级、事件前变更数、直连受影响设备数、到影响面跳数），**不注入分数、不注入排序**。规则结论仅在 LLM 与门禁都给不出任何假设时补位，且补位后 `source` 置 `RULE_FALLBACK`、每条假设标 `origin`。
3. **拒答由确定性纯函数门禁负责，不交给模型自觉。** 同一判据 `isExplainedType(type)`（复用 `fallback.ts` 的口径，外提为单一事实来源）设两个调用点：`gateContext` 在 `produceResult` 之前，命中则**直接调用现有 `ruleFallback(ctx)`**（它本就返回空假设），`source` 保持 `RULE_FALLBACK`、`tokensUsed=null`、`degradedReason` 写明闸门命中 R1；`gateHypotheses` 在 `verifyHypotheses` 之后做纵深防御，逐条清空"无可归因证据"的假设。「可归因证据」只认已登记类型的 ALERT 与早于首告警的 CHANGE——TOPOLOGY 说明不了"为什么坏"，CASE 是类比不是本次证据，METRIC 单独不足以支撑根因。R1 只看**未抑制**告警并用既有的 `beforeFirstAlert`，不重算时间戳。
   **拒答放在前置而不只放后置，两个理由**：一是 0 token——后置门禁必须先调模型才能判断，PRD 要求这类场景不花 token；二是口径统一——前置能命中就说明"事件里没有任何可归因证据"，这个判断与模型输出无关，先做掉可以避免"模型编了一条 → 后置清空 → 但仍付了一次调用与一次修复重试"的浪费。
   **不新增 `source` 枚举（不加 'GATED'）**：`evals/metrics.ts` 的 `fallbackRate` 与前端联合类型都按 `'LLM' | 'RULE_FALLBACK'` 二值判断，加第三个值会让全部历史对比与现有页面同时失效；门禁事实用 `meta.gate` 承载即可。
4. **延迟与 token 预算按 PRD §1 执行，靠"减输出 + 减输入 + 止损"，不靠换模型或加机器。** 输出侧按 PRD AC-6 收紧（verifySteps 1~2、actions ≤1、evidence ≤3、desc ≤80）、`max_tokens=2400` 并采集 `usage.completion_tokens` 与 `finishReason`；输入侧砍历史案例正文与指标趋势明细以满足单事件 <4000 token；修复重试加止损条件；超时拆为首调 12s / 修复 8s。不砍候选数量、不关证据校验。
   **`max_tokens` 取 2400 而非 900**：按 schema 上限逐字段估算，单条假设最坏 ≈1100 token（cause 120 + evidence 3×80 + verifySteps 3×160 + actions 2×120 + 结构字段），三条约 3300，现实输出 1500~2200；900 会稳定截断并触发止损，反而把 `source` 打回 `RULE_FALLBACK`。原有 49017/8≈6127 是输入+输出的总量，不能当输出量用。验收改为截断率（`finishReason=length` 占比）< 5%，低于 2% 才允许下调到 1800 复测。

## Consequences

正面：

- LLM 路径的归因能力与其准确率来源可分离统计。`top1ByOrigin` + `A/B/C` 三组对照 + `hintOnlyTop1` 朴素基线，能回答"提升是模型的还是规则的"这个问题，而不是只看一个总数。
- test-07 这类对抗例由可单测锁死的纯函数保证，不再依赖提示词措辞。规则路径行为不变（它在这些场景本来就返回空）。
- 字典注入同时把 `isExplained` 这个内部概念显式化了：模型看到的"未登记"与门禁用的判据是同一件事，提示词与校验器的口径不再漂移。

负面 / 代价：

- 延迟门禁按 `REASONING` 阶段 < 8000ms / P95 < 12000ms 判，整条 `runAnalysis` 只报告不设门禁（它含取数与落库，现有 8969/14991ms 不能当阶段基线）。阶段埋点目前不存在，属本期实现范围——埋点不上线，这条门禁无法判定。
- `max_tokens=2400` 与 AC-6 的输出上限收紧会互相拉扯：上限越紧越省 token，也越容易截断。截断率 ≥10% 不可接受，处理顺序是"先看骨架与 max_tokens，再考虑放宽上限"，**不允许**靠加修复重试把截断吃掉（那会直接顶掉 P95 目标）。
- `prompt.ts` 从 150 行涨到约 165 行，`analyze.ts` 必须拆出 `produce.ts` 才能守住 300 行（现 323 行已超）。
- `HypothesisSchema` 上限收紧是一次契约变更：`AnalysisResult` 的类型不变，但输出越界更容易触发修复重试。PRD 要求一次通过率 ≥95%，两者存在张力，必须 prompt 骨架与 schema 同批改。
- 字典注入有把 category 拉偏的真实风险（`LINK_DOWN` 成因在上游光路的场景）。缓解是冲突条款 + 用既有 `dev-02`/`dev-11`（LINK_DOWN 存在且标注 LINK）当回归护栏，不是消除风险。
- 规则补位会让 `fallbackRate` 上升。这是诚实的代价：宁可让"这次结论是规则给的"被看见，也不许它顶着 `source=LLM` 混进模型指标。

## Alternatives

**A. 只调提示词，不引入任何结构化先验。** 最小改动，但修不好 test-01 的设备选择，且没有可判定的度量来判断"调好了没有"。否决：无法证明提升来源。

**B. 把 `ruleFallback` 的 Top1 与分数作为"机器初判"拼进 prompt。** 效果最直接，test 集能立刻接近 85.7%。否决：这是刷分——评测集的分母、规则与 LLM 的差距（28.6 点）都会被抹平，而线上没有标注，模型与规则的判断无法互校，错误会以"两个都这么说"的形式变得不可质疑。

**C. 强制走规则引擎，LLM 只做自然语言润色。** 准确率稳定（85.7%）且延迟可控，但放弃 LLM 处理长尾场景的能力，也放弃了"未登记类型 + 复杂证据"下模型可能给出的合理推测。否决：违背产品定位。

**D. 双模型投票 / 换更大模型。** 不改架构只堆算力，延迟与成本都会上去，与"不动模型、不加机器压到 8000ms"的目标直接冲突。否决。

**E. 把门禁做进 `verifyHypotheses`（扩成 L4）。** 否决：校验器的语义是"这条证据是否支撑这条假设"，而门禁的语义是"这次事件有没有可归因的证据"。两者混在一个函数里，会让 `dropped` 的统计口径失真，也会让"该拒答"与"证据不足"这两类失败不可区分。纯函数分开，单测才能各自锁死。

**F. 只做前置门禁（PRD §2.1 R1 的字面实现）。** 成本最低且天然满足 `tokensUsed=0`，但它在模型之前，看不到模型输出，挡不住"上下文里有一条已登记告警、模型却只引用未登记证据"的情况（test-07 的变体会漏）。否决：单点判定覆盖不了证据级失效，改为同一判据设两个调用点。
