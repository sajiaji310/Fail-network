## 1. 结论先行

NetScope 已经不是概念 Demo，而是一个具备完整纵向闭环的 MVP：

```text
告警接入 → 归一化/抑制 → 事件聚合 → 根因候选 → 证据校验 → 人工裁决 → 结案报告/案例沉淀
```

项目最有价值的设计不是“接入了 LLM”，而是把模型放在可控的业务流程中：

- 规则引擎先生成候选，避免模型从零猜测。
- LLM 输出受 Zod schema 约束。
- L1/L2/L3 证据校验减少无依据输出，并保留审计信息。
- 人工采纳/否决是明确的产品动作，而不是把模型结果直接当真相。
- 结案后生成报告和案例，形成知识沉淀闭环。

当前项目适合作为作品集和 AI 运维工程实践。还不适合宣称已经验证了真实生产价值：分数是规则下限，历史回填验不了研判，控制台没有登录。下一阶段按第 0 节做，不要再扩功能面。

## 4. 主要问题与风险

以下问题按对产品价值和生产安全的影响排序。

### P0-1：生产边界没有安全保护

> 复核：部分落地。`APP_ENV=production` 时写接口要 `x-api-key`，角色不足返回 403，有内存限流，Compose 把 3000 和 5432 绑在 `127.0.0.1`。页面和普通读接口仍不鉴权，限流计数不能跨进程。

当前 API 没有鉴权和限流，且存在可写接口：

- `POST /api/v1/ingest/alerts`
- `POST /api/v1/ingest/simulate`
- `POST /api/v1/correlation/run`
- `POST /api/v1/incidents/[id]/analyze`
- `PATCH /api/v1/incidents/[id]`
- `PATCH /api/v1/incidents/[id]/hypotheses/[hypothesisId]`
- `POST /api/v1/incidents/[id]/report`

这在本地 MVP 中可以接受，但 Docker Compose 默认暴露 `3000` 和 `5432`，一旦部署到公网或共享网络，任何能访问服务的人都可能注入数据、触发模型调用、修改事件状态或制造大量报告。

**建议：**

1. 增加 `APP_ENV=local|staging|production`。
2. `production` 环境默认拒绝无鉴权请求。
3. MVP 可以先实现单用户 API Key 或反向代理 Basic Auth，不必立即做完整 RBAC。
4. 对导入、研判、报告生成分别增加 IP/用户维度限流。
5. Docker Compose 默认只绑定 `127.0.0.1`，不要默认暴露 PostgreSQL 到所有网卡。
6. 对 `reset`、模拟注入和批量导入增加明确的管理员权限校验。

### P0-2：健康检查可能泄露数据库内部错误

> 复核：已落地。`/api/health` 只回 `status` / `db` / `llm`。存活看 `/api/live`，就绪看 `/api/ready`。

`src/modules/system/service.ts` 将数据库异常写入 `dbError`，`src/app/api/health/route.ts` 又直接把整个状态对象返回。生产环境下，连接字符串、主机名、端口或驱动错误可能被外部探测到。

**建议：**

- 对外健康接口只返回 `{ status, db, llm, traceId }`。
- 详细错误只写结构化日志，并通过内部诊断接口或监控系统查看。
- 增加 `/api/ready` 与 `/api/live`：存活检查不依赖数据库，就绪检查才检查数据库。

### P0-3：test 集的核心压缩目标没有达成

> 复核：口径已修正，不要再当聚类缺陷修。分组压缩比、处理单元、二次收敛都已落地。留出集 54 条告警 / 9 个标注事件，理论上限就是 6.0:1，压缩效率 100%。绝对比值要上去，只能换平均每事件不少于 8 条告警的数据。

当前留出集结果：

- Top1：85.7%（6/7）
- Top3：85.7%（6/7）
- 事件精确率/召回率：100%/100%
- 误抑制率：0%
- 告警压缩比：6.0:1，目标 8:1，未达标
- 全通过场景：7/8

这说明事件识别和根因候选已经有较强的演示效果，但告警压缩仍有真实欠账，不能在产品介绍中只强调 Top1/Top3 而忽略压缩比。

**建议：**

1. 先把压缩比定义拆成整体、正例、干扰例、对抗例四组，不用一个总平均数掩盖差异。
2. 增加“用户实际需要处理的告警数”指标，而不仅是数据库中的告警行数。
3. 针对长期悬挂告警设计二次收敛规则：同指纹、同设备、同事件在跨窗口后如何继续合并。
4. 增加误抑制成本指标：关键根因告警被抑制时应单独计为 P0 失败。

### P0-4：缺拓扑时系统没有明确的产品降级策略

> 复核：已落地。详情页有完整 / 部分缺失 / 完全缺失，非完整时结论标成候选排序，置信度上限 0.75 / 0.55。test-08 仍是未命中，这是降级后的正确记分，不要调阈值让它变绿。

`test-08` 和 `dev-13` 已经暴露这个边界：拓扑缺失时，事件覆盖设备和根因召回都会退化。问题不是“算法再调一个阈值”就能完全解决，而是产品需要告诉用户当前结论的可信边界。

**建议：**

- 在事件详情页展示“拓扑完整度”：完整、部分缺失、完全缺失。
- 当拓扑不足时，将“根因结论”改为“候选排序”，并显示缺失设备/链路数量。
- 增加不依赖拓扑的备用信号：同设备时间序列、告警类型共现、变更先后、外部系统关联 ID。
- 评测中单独报告“拓扑完整”和“拓扑缺失”两组成绩。
- 不要在拓扑完全缺失时继续展示过高的置信度。

### P1-1：事件生命周期仍缺少可审计的状态历史模型

> 复核：未做。`statusLog` 和 `closure` 仍是 JSON。自动重开不走状态机，再次结案会覆盖上一份 `closure`。不影响当前闭环。

当前 `Incident.statusLog` 使用 JSON 保存状态流转记录，`closure` 也使用 JSON 保存结案信息，适合 MVP，但后续会遇到：

- 无法按操作者、时间、状态做查询。
- 并发修改时难以判断谁最后一次推进了状态。
- 自动重开不经过人工状态机，审计链路不完全统一。
- 结案被再次重开后，历史结案信息可能被覆盖。

**建议：**

P1 阶段增加 `IncidentEvent` 或 `IncidentStatusHistory` 表，记录：

```text
id, incidentId, fromStatus, toStatus, actorType, actorId,
reason, note, createdAt, traceId
```

JSON 可以作为兼容读模型保留一段时间，但新写入应逐步转到事件表。

### P1-2：告警导入是逐条串行处理，吞吐和并发一致性不足

> 复核：只做了一半。`IngestBatch` 已能对超过 500 行返回 202 并写进度。循环里仍是逐条 `recordAlert`，瓶颈是每行 2–3 次查询。批次推进还在本进程，重启后由 `sweep` 标 FAILED。

`src/modules/ingest/service.ts` 在循环中逐条调用 `recordAlert`。这对 500 条以内的演示数据足够，但生产数据接入后会有两个问题：

- 每条告警都有多次数据库往返，批次耗时线性增长。
- 两个相同批次并发导入时，预查询 `externalKey` 的结果可能过期，仍需要依赖数据库唯一键和重试逻辑兜底。

**建议：**

- 将输入分成“设备解析、外部 ID 去重、指纹解析、周期归并、抑制回溯”几个批处理阶段。
- 对同一 `source + externalKey` 增加更明确的唯一约束或导入批次表。
- 导入接口返回 `batchId`，异步处理时查询批次进度。
- 继续保留逐条失败，不要因为一条脏数据回滚整个批次。

### P1-3：HTTP 输入校验存在不一致

> 复核：已落地。研判请求体是 `z.object({ force: z.boolean().optional() })`。写路由经 `readTextLimited` 边读边计数，chunked 超限返回 413。

绝大部分路由使用 Zod，但 `src/app/api/v1/incidents/[id]/analyze/route.ts` 直接把 JSON body cast 成 `{ force?: unknown }`。这绕开了项目规定的“外部输入必须由 `unknown + zod` 收窄”。

另外，告警导入的 2MB 限制主要依赖 `Content-Length`。对 chunked 请求或缺少该 header 的请求，不能保证真正限制读取体积。

**建议：**

- 为所有请求体定义独立 schema，即使只包含 `force` 一个字段。
- 读取请求体时使用流式大小限制，超过阈值立即中止。
- 对 `content-type`、编码、CSV 行数和单条 message 长度分别设限。

### P1-4：工程规则已被当前代码突破

> 复核：仍在。2026-11-21 行数：`correlation/service.ts` 446、`hypothesis-panel.tsx` 426、`case/service.ts` 399、`settings/page.tsx` 390、`overview/page.tsx` 321、`fallback.ts` 328。运行不受影响。下次改这些文件时再按职责拆，不要为了行数单独开一轮。

项目约束规定单文件不超过 300 行，但当前实现中已经存在明显超限文件：

- `src/modules/correlation/service.ts`：约 422 行
- `src/modules/correlation/service.test.ts`：约 402 行
- `src/app/(console)/overview/page.tsx`：约 366 行
- `src/modules/alerts/lifecycle.test.ts`：约 366 行
- `src/modules/rca/fallback.ts`：约 357 行

这不会立即造成运行错误，但会增加上下文负担、降低模块边界清晰度，并让后续 Agent 修改更容易产生回归。

**建议：**

- 不要机械拆文件，按业务职责拆：
  - correlation：候选加载、事件归属、事件合并、结果汇总。
  - overview：数据查询、指标卡片、评测卡片、任务卡片。
  - fallback：候选生成、分数计算、标题/证据构造。
- 把“业务规则常量”和“纯计算函数”保持在独立模块。
- 将文件行数检查加入 CI，但先对现有超限文件建立豁免清单，再逐步消化。

### P1-5：评测集规模和 LLM 评测仍不足以支撑生产结论

> 复核：未做。test 仍是 8 个场景、分母 7，全部跑在规则降级上。对外只说「规则下限 Top1 6/7」。补跑真实模型之前，不要写模型准确率。

当前 test 集只有 8 个场景，Top1/Top3 的有效分母是 7；一个场景就可能造成约 14 个百分点波动。且现有结果主要来自无 Key 的规则 fallback，无法证明真实 LLM 的输出质量、成本和延迟。

**建议：**

- 扩展到至少 50 个场景，再分为 dev/test/held-out 三组。
- 正例、干扰例、对抗例不要只按数量平均，还要按业务影响加权。
- 增加双人或多人的根因标注，记录可接受的多个答案。
- 对 LLM 评测固定模型、temperature、prompt 版本和采样次数。
- 增加成本指标：tokens、单事件费用、超时率、fallback 率、schema 修复率。
- 增加“人工接受率”和“平均到达可用结论时间”，这是产品价值比模型命中率更接近的指标。

### P1-6：报告和案例的来源可信度还可以更清晰

> 复核：已落地。结案时有人工采纳才标 `VERIFIED`，研判召回只取已验证案例。未确认案例留在库里可查，不进上下文。报告仍会带上未采纳结论，并标明未经人工确认。

系统允许未人工确认的假设进入报告和案例，并通过文字标注“AI 推断，未经人工确认”。这在 MVP 中可以接受，但案例库长期积累后，未经确认的错误结论会反过来污染下一次研判上下文。

**建议：**

- 案例增加 `verificationStatus`：`UNVERIFIED / HUMAN_CONFIRMED / REJECTED`。
- 默认只将人工确认案例召回给模型；未确认案例只在 UI 中可检索。
- 案例增加 `sourceIncidentId`、`acceptedHypothesisId`、`verifiedBy`、`verifiedAt`。
- 对被否决的假设记录反例，未来评测中作为负样本使用。

## 5. 产品体验建议

### 5.1 概览页应从“工程验收面板”逐步转为“值班决策面板”

> 复核：已落地。首屏是活跃、未接手、响应告急、待确认，加三个队列。种子基线和交付进度在 `/settings`。

当前概览页同时展示环境健康、种子基线、告警状态、事件、评测和任务卡进度，适合项目验收，但值班人员最关心的是：

1. 当前是否有 P0/P1 事件。
2. 哪些事件还没有人接手。
3. 哪些事件已经有可信根因。
4. 哪些事件即将超出响应目标。

**建议调整：**

- 首屏第一块改为“需要立即处理的事件”。
- 将 P0/P1 活跃事件、持续时间、影响设备、是否已研判作为主指标。
- 将 T01-T09、评测基线和种子数据放到“系统状态”或设置页。
- 增加“未研判”“证据不足”“等待人工确认”三个工作队列。

### 5.2 事件详情页应强化“下一步行动”

> 复核：阶段条、验证勾选、业务影响面已落地。高风险动作仍只在结案时给出未完成验证的警告，不阻断。

当前三栏结构已经完整，但用户仍需要在根因卡片、时间线、处理动作之间自行组织动作。

**建议增加：**

- 顶部明确展示当前阶段：`待接手 / 分析中 / 已定位 / 缓解中 / 待确认 / 已恢复`。
- 每条假设增加“为什么排在这里”的短解释。
- 将验证步骤变成可勾选清单，保存验证结果和操作者。
- 对高风险动作显示“需要审批”，并在结案前提示未完成验证项。
- 影响面加入业务服务维度，而不是只显示设备数量。

### 5.3 处理流程需要“接手”动作

> 复核：已落地。有接手、转派、释放和按严重级快照的响应时限。`assignee` 仍是手填名字，没有用户表。

目前事件可以直接从 `OPEN` 跳到后续状态，但缺少明确的责任人和接手动作。多人协作时容易出现“大家都看到了，但没有人负责”。

**建议：**

- 增加 `assignee`、`claimedAt`、`team`。
- 第一个动作是“接手事件”，而不是直接“分析”。
- 概览页显示未接手事件和已超时未响应事件。
- 后续再接入通知、值班表和 RBAC。

### 5.4 解释“置信度”而不是只展示数字

> 复核：未改文案。缺拓扑时已经压上限并改称候选排序，数字本身仍叫置信度。

`confidence` 容易被用户理解为模型准确率。建议在 UI 上改成：

- “证据支持度”或“当前排序分”。
- 显示证据数量、拓扑完整度、变更关联、历史案例命中等组成信号。
- 当拓扑缺失或证据不足时，显著降低表达强度。

## 6. 推荐迭代顺序

> 复核：下面四段是 2026-11-20 的计划，第 1–4 阶段的条目都已按 `docs/STATE.md` 落地。下一轮只做第 0 节那张表，从历史回放和批量入库开始。

### 第 1 阶段：生产边界与数据可信度

目标：让 MVP 可以安全地被别人试用。

- 增加 API Key/反向代理认证。
- 关闭公网默认暴露数据库。
- 健康检查脱敏，增加 live/ready 分离。
- 完成请求体流式限制、限流和审计日志。
- 增加 `verificationStatus`，防止未确认案例污染召回。

### 第 2 阶段：补齐核心算法欠账

目标：把“能演示”提升为“可解释、可重复”。

- 解决长期悬挂告警的跨窗口收敛。
- 定义拓扑完整度和缺拓扑降级策略。
- 增加事件拆分的人工操作入口。
- 增加独立事件、并发故障、时钟漂移、乱序上报和重复批次测试。
- 扩充评测集并增加人工接受率、成本、延迟指标。

### 第 3 阶段：提升值班效率

目标：减少用户从看到事件到采取动作的时间。

- 增加接手、负责人、团队和响应时限。
- 概览页切换为“待处理队列”视角。
- 验证步骤可勾选并记录结果。
- 增加服务影响面和业务依赖。
- 对研判过程提供阶段进度，之后再升级为 SSE。

### 第 4 阶段：真实数据接入和规模化

目标：验证真实网络环境中的价值。

- 接入 Prometheus/Zabbix/Syslog 中至少一种真实数据源。
- 导入改为批处理/异步任务，提供批次状态。
- 引入指标快照或时序数据，避免只依赖告警瞬时值。
- 完成多租户、RBAC、审计查询和数据保留策略。
- 在真实事件上测量 MTTR、人工接受率和误抑制成本。

## 9. 最终判断

闭环和证据校验仍然是这个项目最强的部分。短板已经不是「缺鉴权、缺拓扑降级、缺真实源」，而是：历史数据聚不成事件、入库仍逐行、控制台不登录、评测没有真实模型对照。

下一版目标保持这句话：

> 让一个陌生运维人员在安全边界内，能够从告警风暴中找到一个可解释、可验证、可追责的下一步动作。

要靠近它，控制台登录、历史回放和批量入库已经补上。压缩比和 test-08 不用再修。进程外队列仍等多实例再做。
